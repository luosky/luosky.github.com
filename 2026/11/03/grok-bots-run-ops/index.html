一人公司的运营部：一群 Grok bot 每天自己开会、提需求、盯数据

Nov 3rd, 2026 • Permalink

我叫 Luosky，本科上海交大，做了 20 多年互联网应用开发。现在我在做 Gigle Tutor，一个辅导孩子学数学的 AI 家教。

说是一个人在做，其实我身边有一群 AI 同事：写代码的、审代码的、看数据的、跑运营的。我留给自己的，主要是拍板和合并代码。这个系列记录的，就是这家「一人公司」里真实发生的事。

这一篇讲我的运营部。它由一群 Grok bot 组成，每天自己开会、提需求、盯数据。

我挑一件真事来讲：注册转化的问题，怎么从运营群里的一句话，变成三个上线的改动。

一、日报一发，运营 bot 先问了一句

每天早上 6 点，gigle_data 会把前一天的网站数据整理成日报，发到运营群里。

那天日报发出后，群里的运营 bot 问了一句：点注册按钮到注册成功，转化率为什么这么低？拉一下历史曲线看看。

gigle_data 没有只甩出一条曲线，而是把「点了注册、却没注册成功」的人拆开来看：

  1. 有人其实是老用户，点注册是为了登录，或者在重试；
  2. 有人卡在了验证邮件上：在 App 的内置浏览器里打开验证链接，页面直接报「链接已失效」；
  3. 日语和英语界面的注册按钮，压根没算进点击里；
  4. 剩下的，才是打开注册弹窗又走掉的新访客。

这个结论发在群里，gigle leader 看到了，主动接过来提了需求。

二、运营群里的几位同事

先介绍一下出场的几位。它们都是我在 Grok 里配的 bot，在一个叫「Gigle 运营群」的群里：

  1. gigle leader：我的大内总管。我一般只和它对接；其他 bot 有事都向它反馈，它能处理的自己处理，处理不了的才上升给我。方案出来了，也由它拍板。
  2. gigle_data（数据 bot）：看网站数据，每天早上出日报。
  3. gigle_x、gigle_ins、gigle_tk：分别运营 X、Instagram、TikTok 账号。
  4. 提需求 bot：不在群里。它专门把需求提到 GitHub 上，再把 GitHub 那边的回复带回来。它从不自己合并代码。

它们平时在群里就是这样互相派活的：

真实记录：运营群里，gigle leader 给 gigle_data 交代上线后要核对的数据

GitHub 那边是另一拨 AI，叫 cavil-loop，已经跑了半年多。它是一个基于 GitHub issue 的多 agent 编程框架：拿到一句话需求，会结合项目代码自动出设计方案，AI 评审方案，AI 写代码，再由 AI 做代码评审和测试。

三、需求交到 GitHub

gigle leader 把 gigle_data 的分析交给提需求 bot，由它提到 GitHub 上。

让我印象很深的是，gigle leader 在需求最后主动加了一句隐私要求：

第 1、2、4 条的新埋点只记 mode、语言、错误类型这类字段，不要带 URL 的 # 部分、邮箱或 token。

前几天，bot 们刚发现过一个隐私问题。从那以后，它每提一个需求都会带上这句。

需求到了 GitHub，查重、拆分就是 cavil-loop 的事了：先查已有的 issue，避免重复，再拆成 3 个，各自往下做。提需求 bot 把结果回报给 gigle leader：

真实记录：提需求 bot 回报 gigle leader，注册转化的需求在 GitHub 上变成了 3 个 issue

四、两拨 AI 来回过招

整个流程画出来是这样的：

真实记录：一个需求在 Grok 运营 bot 和 cavil-loop 之间走完的顺序（泳道图，红框按步骤走）

每个 issue，AI 程序员都先出方案，不急着写代码。方案要先过复审，复审会打回，三份方案都改了几版才过。

方案里需要拍板的地方，会写成选择题。提需求 bot 把方案带回群里，gigle leader 看完，只回了这样一句：

1366 A；1367 Q1 B，Q2 A

有一处让我挺意外。第三个需求说的是「后台的注册用户数，和统计里的注册事件对不上」。AI 程序员没有照着需求直接去补，而是先逐个账号核对了一遍，发现两边比的根本不是同一段时间：一边是全部历史账号，一边只是最近几天的事件。漏记的账号确实有，但只是一小部分；具体为什么没记到，到现在也不能确定，浏览器把统计请求拦掉、原来判断「刚注册」的方式有缺口，都有可能。所以它没有去赌某一个原因，而是改成由我们自己的服务器盯着新账号上报，不再依赖浏览器发送。

代码写完，同样要过复审。复审通过后，提需求 bot 再把验收请求带回群里。gigle leader 认可的不是「这个需求」，而是具体的某一次提交：

A，认可 dbbc67d6b，交维护者合并。

后来两个改动撞在了同一处，解决冲突后提交号变了，它又对新的那次提交重新认可了一遍。

最后一步是我：验收、合并。合并之后，代码会自动部署上线。

五、上线之后，先别急着下结论

新的邮箱验证页上线后，gigle leader 让 gigle_data 盯一下上线后的数据。gigle_data 自己建了一个每两小时查一次的检查：

真实记录：gigle_data 收到 gigle leader 的叮嘱后，新建了每两小时一次的检查

当天晚上，这个检查真的盯到了一批「链接已失效」。

gigle_data 的第一反应是，看着像是我在测试。但 gigle leader 没让它急着下结论：

目前还不能确定是测试，我已经跟维护者问测试时间段了，拿到就转给你。在这之前先把这段时间标成"待确认"，暂时不要在群里下结论。

问题经提需求 bot 带到了 GitHub 上。我告诉 gigle_data：不是我在测试。

它接着往下查。按它的分析，其中一部分是一位老用户，在不同的浏览器里反复打开早先那封旧验证邮件；剩下的几条，它推测也是这位用户，但没法确认。

我回了一句：跟 leader 说是虚惊一场就好了。

不过新注册用户的验证效果到底怎么样，还要接着看数据。

六、两边是怎么接上的

Grok 和 GitHub 是两个完全不同的系统。它们之间只靠两样东西：GitHub issue 上的标签，和「叫一声」。

轮到 AI 程序员干活，issue 上挂一个标签；轮到 Grok 那边回话，就换另一个标签，再叫它一声，它过来把挂着这个标签的条目都拉走，转给群里，再把回复原样贴回来。

两边谁都不用记对方的聊天记录，issue 就是唯一的事实来源。

七、我还要做什么

这家一人公司里，我留给自己的是两件事：

  1. 拍板。提需求 bot 说，它只有在产品决定、成本、隐私这类事上，才会来打扰我。
  2. 上线前的最终验收和合并。bot 们从不自己合并。

不过这套流程已经跑了半年多。一开始，验收时经常能发现问题；现在，基本上一次就过。接下来可以考虑让它自动合并，免得瓶颈卡在我这里。

我问 gigle leader：这套协作，哪一步最省事？

A/B 验收。编程 agent 先出方案、过评审，再把要我定的点写成 A/B 选项，我只回一个字母加条件，几分钟就能走一轮。

那哪一步最容易出岔子？

多个 bot 之间转述，以及「合并」和「上线」之间的空档。

所以它给自己定了两条规矩：每个结论都回到数据核对；上线以通知为准，不以合并为准。

彩蛋：这篇文章的素材，也是这么来的

我在 GitHub 上开了一个「写这篇文章」的 issue。cavil-loop 先把自己这一侧的记录搜集齐，再挂个标签，跟 Grok bot 要它们那边的素材，最后写成了这篇。

真实记录：我的 GitHub 项目看板上，写这篇文章的 issue 和它的 PR 都排在本周的迭代里

提需求 bot 先交了它自己能看到的那部分，群聊记录它看不到，就转请 gigle leader 去收集。gigle leader 收集好，又交回提需求 bot 贴到 issue 上：

真实记录：gigle leader 把收集好的素材交给提需求 bot，让它贴到写这篇文章的 issue 上

你上面读到的大部分细节，就是这么来的。

文中让 AI 程序员在 GitHub 上接需求、出方案、互相复审的那套流程叫 cavil-loop，已经开源：github.com/GigleAI/cavil-loop。
